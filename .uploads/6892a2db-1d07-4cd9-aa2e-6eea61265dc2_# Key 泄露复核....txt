## 一、结论

**完整 API Key / Bearer 字面量 / JWT / 私钥：53 个目标文件与 649 条会话记录中全部未发现；送审 HTML 里也没有 key 字面量。**

但「文件里没有 key 字面量」**不等于没有泄露风险**，本轮挖出三条实质问题：

1. **既成事实**：两把上游 key 曾在对话中完整明文出现、未轮换未删除（第四节 L1），攻击者可绕过网关直接调付费模型。

3. **证据包自身曾泄露前缀**：v4 合并第 1 批旧 MANIFEST 时回流了 K1/K2 真实前缀，本轮已在打包脚本输出阶段强制脱敏并重生成（3.2），旧版 v2/v3 与工作区报告也已清除。

## 五、三个核心诉求的本轮判定

| 诉求 | 本轮结论 | 依据 |
|---|---|---|
| ① 前端产物 / App 包零 API Key | **字面量层面成立**（HTML 全文扫描未发现）；**运行时不成立**：L10 的 BYOK 通道可在浏览器/WebView 注入并持久化 key，且可把 key 发到任意 baseUrl；App 包无产物可验 | 3.1 / 3.2 / L10 |
| ② 永不产生账单 | 与 Key 泄露相关但不等价：L1 的旧 key 若仍有效且已泄露，攻击者可**绕过网关直接调付费模型** —— 网关白名单只约束经过网关的流量 | AAA.md L1–L4、Q1 |
| ③ 转 App 后仍成立 | 设计层成立（不把 key 打进包），现状层无产物可验 | 10-app.md、L8 |

## 六、上线前必须处置（按紧急度）

1. **轮换并删除 K1/K2**：唯一「已经发生」的泄露，在网关之外，任何前端/网关加固都补不上。
